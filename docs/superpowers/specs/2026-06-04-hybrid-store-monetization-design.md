# Hybrid Store Monetization Design

## Goal

为 `desktop-ai-companion` 设计一套可扩展的商城计费与权益模型，满足以下目标：

- 前台首发阶段继续主推现金直购，降低购买门槛。
- 后端同时预留积分体系，避免后续商品增多后重做数据结构。
- 明确区分“内容所有权”和“服务订阅权益”，避免会员逻辑误伤已购内容。
- 用统一商品模型支撑后续大量角色、舞蹈动作、歌曲和内容包扩展。

## Product Direction

用户已明确选择以下商业化方向：

- `VIP / SVIP` 继续按月订阅，首发阶段主走现金购买。
- `角色 / 舞蹈动作 / 歌曲 / 未来内容包` 以单品售卖为主。
- 后端预留积分兑换能力，但第一阶段前台可以不展示积分入口。
- 已购角色、已购舞蹈动作和已购歌曲属于永久内容权益，不能因会员到期被收回。

## Core Decision

采用 **混合制商品模型**：

- 会员商品只支持现金购买。
- 内容商品同时支持：
  - `cash_price_fen`
  - `point_price`
- 前端第一阶段主展示现金价。
- 后端第一阶段先打通：
  - 商品列表返回
  - 用户权益返回
- 后续再补：
  - 内容商品下单
  - 积分账户
  - 积分兑换
  - 支付成功后授予权益

这是当前范围最稳的切法，因为它保留了首发转化效率，也避免后面重新设计商城底层。

## Why Not Pure Direct Purchase

纯直购制虽然最简单，但它有两个明显问题：

- 后续做活动、签到、礼包、赠送会很别扭。
- 商品一多，所有销售动作都会被绑定在现金支付流程上，运营空间太小。

所以纯直购适合首发展示，不适合作为底层唯一模型。

## Why Not Pure Points

纯积分制虽然运营灵活，但不适合作为首发主交易方式。

问题在于：

- 用户需要先理解积分，再理解商品兑换，心智成本更高。
- 用户需要多走一步“先充值积分”，容易降低首单转化。
- 当前项目还没有足够强的活动体系去放大积分制优势。

因此，纯积分可以作为后续增强方向，但不应成为第一阶段主路径。

## Recommended Pricing Anchor

建议先把积分锚点固定为：

- `1 积分 = 0.01 元`
- `5 元角色 = 500 积分`
- `5 元舞蹈动作 = 500 积分`
- `1 元歌曲 = 100 积分`

这能保证：

- 现金价和积分价换算直观
- 后端逻辑简单
- 以后做赠送积分、充值送积分时不需要改商品语义

运营层可以后续引入更大积分包折扣，例如：

- `500 积分 = 5 元`
- `1100 积分 = 10 元`
- `2300 积分 = 20 元`

但商品基础兑换锚点先保持稳定。

## Ownership And Service Rules

这是整套模型里最重要的业务边界。

### 内容所有权

以下内容属于永久内容权益：

- 角色模型
- 舞蹈动作
- 歌曲内容
- 未来静态内容包

用户一旦购买成功：

- 内容永久解锁
- 免费状态下仍可基础使用
- 会员到期后不得回收

### 服务订阅权益

以下内容属于订阅服务权益：

- 更高模型权限
- 更高聊天额度
- 语音对话额度
- 会员专属音色
- 云同步 / 跨设备同步能力

这些能力由 `VIP / SVIP` 控制：

- 开通时可用
- 到期时关闭
- 不影响用户已购买的角色、舞蹈动作和歌曲

### Hard Rule

后端必须保证以下规则始终成立：

- 不允许出现“已购角色因会员到期不可用”
- 不允许出现“已购舞蹈动作因会员到期不可播放”
- 不允许出现“已购歌曲因会员到期不可使用”
- 会员只影响高级服务，不影响已购内容所有权

## Product Model

商品必须有稳定 `product_code`，但不能依赖前端硬编码。

正确模型是：

- 后端统一维护商品定义
- 前端只拉商品列表
- 用户是否已拥有某项内容，只看后端返回的权益数据

这意味着即使未来有上百个角色、舞蹈动作和歌曲，系统也不需要为每个商品单独写分支逻辑。

## Data Model

建议将商城底层拆成四类核心数据。

### 1. `store_products`

职责：

- 定义“卖什么”
- 定义“卖多少钱”
- 定义“商品对应什么资源”

建议字段：

- `product_code`
- `product_name`
- `product_type`
- `cash_price_fen`
- `point_price`
- `status`
- `payload_json`
- `created_at`
- `updated_at`

其中：

- `product_type` 可取：
  - `membership_plan`
  - `character_item`
  - `dance_item`
  - `music_item`
  - `content_bundle`
  - `point_pack`
- `payload_json` 用于放资源路径、展示素材、附加元数据

### 2. `user_entitlements`

职责：

- 定义“用户实际拥有什么内容或资格”

建议字段：

- `user_id`
- `entitlement_code`
- `entitlement_type`
- `source_product_code`
- `status`
- `expires_at`
- `payload_json`
- `created_at`
- `updated_at`

其中：

- 永久角色、舞蹈动作和歌曲通常使用 `expires_at = NULL`
- `entitlement_type` 可用于区分：
  - `permanent`
  - `time_limited`
  - `service_flag`

### 3. `user_point_accounts`

职责：

- 保存用户当前积分余额

建议字段：

- `user_id`
- `balance`
- `created_at`
- `updated_at`

### 4. `user_point_ledger`

职责：

- 记录每一笔积分变动流水

建议字段：

- `user_id`
- `change_amount`
- `source_type`
- `source_order_no`
- `remark`
- `created_at`

这样可以清晰地区分：

- 商品定义
- 用户拥有内容
- 用户积分余额
- 积分增减历史

## API Shape

### Phase 1: Minimal Read APIs

第一阶段只做读取能力，不急着做完整购买闭环。

#### `GET /store/products`

返回当前上架商品列表。

每个商品至少返回：

- `product_code`
- `product_name`
- `product_type`
- `cash_price_fen`
- `point_price`
- `status`
- `payload`

前端用途：

- 渲染商城列表
- 区分角色、舞蹈动作、歌曲、会员商品
- 为后续购买按钮提供商品标识

#### `GET /me`

除了当前已有的 `user` 和 `membership` 外，扩展返回：

- `entitlements`
- 后续可扩展 `points_balance`

前端用途：

- 判断某个角色是否已拥有
- 判断某个舞蹈动作是否已拥有
- 判断某首歌曲是否已拥有
- 决定是否显示“购买”还是“已拥有”

### Phase 2: Purchase And Grant

第二阶段再补：

- 内容商品下单接口
- 微信支付购买内容商品
- 积分兑换接口
- 支付成功后授予 `user_entitlements`
- 订单区分购买的是会员还是内容商品

这时现有 `payment_orders` 需要扩展出更通用的订单语义，而不是只服务会员订单。

## Order Model Direction

当前订单体系主要围绕会员购买设计，后续建议演进为统一订单模型。

推荐增加以下概念：

- `order_type`
  - `membership`
  - `content_purchase`
  - `point_topup`
- `product_code`
- `grant_status`

这样一个订单体系就可以支撑：

- 买会员
- 买角色
- 买舞蹈动作
- 买歌曲
- 买积分包

而不需要为每种商品做一套独立订单表。

## Initial Scope Recommendation

为了控制当前实现范围，建议按以下顺序推进。

### Step 1

先实现只读基线：

- `GET /store/products`
- `GET /me` 返回 `entitlements`

### Step 2

实现内容商品支付闭环：

- 创建内容商品订单
- 支付回调
- 发放永久权益

### Step 3

实现积分体系：

- 积分账户
- 积分流水
- 积分兑换商品

这个顺序可以保证：

- 前端能先完成“显示商品”和“已拥有态”
- 后端不会因为一次做太多而变得不稳定

## Out Of Scope

本次设计明确不包含以下内容：

- 第一阶段前端完整商城 UI 细节
- 积分签到、任务奖励、优惠券
- 角色、舞蹈动作或歌曲的复杂组合包促销
- 多支付渠道统一抽象
- 内容推荐、榜单、搜索排序

这些都可以在当前底层模型稳定后再补。

## Testing Direction

测试应优先覆盖业务边界，而不是只测字段存在。

第一批测试建议覆盖：

- `/store/products` 能返回有效上架商品
- `/me` 能返回会员与内容权益
- 免费用户已购角色后，`entitlements` 中仍可见该角色
- 免费用户已购歌曲后，`entitlements` 中仍可见该歌曲
- 会员到期后，内容权益仍保留

第二批测试再覆盖：

- 内容商品支付成功后授予永久权益
- 重复回调不会重复发放权益
- 积分余额不足时兑换失败
- 积分流水与余额一致

## Recommendation

当前项目阶段，最稳的方向是：

- `VIP / SVIP` 做订阅服务
- `角色 / 舞蹈动作 / 歌曲 / 静态内容` 做单卖
- 后端统一使用商品表和权益表
- 前台首发主推直购
- 后端预留积分能力但不急着全部开放

一句话总结：

`角色、舞蹈动作和歌曲卖的是内容所有权，VIP 卖的是服务能力；商城前台先简单，后端底层一步到位。`

## Copyright Note

歌曲类商品单卖前必须先确认授权链路。

这条不影响当前底层模型设计，但会影响商品实际上架规则：

- 只有已确认可售的歌曲内容，才允许作为 `music_item` 上架
- 如果歌曲只是舞蹈资源的展示依赖而非可售内容本体，则不单独生成 `music_item`
- 没有明确授权的音乐内容，不应直接作为可售商品发布
